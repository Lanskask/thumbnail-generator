Frontend in Kubernetes, backend on Cloudflare: how they connect

The upload page runs in a local Kubernetes cluster (kind). The thumbnail work (resize, storage) stays in the Cloudflare Worker. This page explains how a click in your browser reaches the Worker and why each piece is there.

1. The path of one request

Browser at http://localhost:8080. The page calls /api?action=upload on its own address.
↓ kubectl port-forward (a tunnel from your Mac into the cluster)
Service thumbnail-frontend: a stable name and address that forwards to whichever Pod is alive.
↓
Pod running nginx (started by the Deployment, which keeps the wanted number of Pods running).
/ → serves index.html  |  /api... → forwards to the Worker.
↓ HTTPS over the internet (a reverse proxy: nginx makes the call on the browser's behalf)
Cloudflare Worker thumbnail-generator.physics-study-dashboards.workers.dev: resizes with the Images binding and stores in R2.

3. How it works in general

kind ("Kubernetes in Docker") runs a whole cluster as one Docker container on your Mac. A cluster is a set of machines (nodes) that run containers for you. You do not start containers yourself. You write desired state in YAML ("keep 1 copy of this image running") and Kubernetes keeps it true: if the Pod dies, the Deployment starts a new one.

The image is built locally, so make k8s-up copies it into the kind node with kind load docker-image. There is no registry. That is why the manifest uses imagePullPolicy: IfNotPresent.

A Pod's IP changes every time it is recreated. A Service gives the Pods a fixed name and IP and spreads traffic across them. Inside the cluster the name thumbnail-frontend resolves through the cluster's DNS. From your Mac you reach it with port-forward; a real cluster would add an Ingress or a LoadBalancer in front.

4. Why nginx proxies /api (the CORS reason)

A browser blocks a page from reading responses of another origin (scheme + host + port) unless that server sends CORS headers (Cross-Origin Resource Sharing). The page is at localhost:8080; the Worker is at workers.dev: different origins. The Worker sends no CORS headers, because until now the page was served by the Worker itself.

With the proxy, the browser only ever talks to localhost:8080. nginx makes the call to the Worker from the server side, where CORS does not apply. The Worker needs no change.

5. Is nginx really necessary?

For serving the page alone: no. It is one static file, so any static file server would do (Caddy, a 10-line Go binary, python -m http.server). Even the Worker already serves this same page.

Here it earns its place for the proxy. The alternatives are all more work:
AlternativeCost
Add CORS headers to the Worker and let the page call the Worker URL directlyEdit and redeploy the backend; the URL is baked into the page. Then any static server works and nginx is not needed.
Ingress controller routing /api to an ExternalName ServiceInstall an Ingress controller in kind (extra moving part) and still deal with the Host header.
Skip Kubernetes; use the Worker's own pageSimplest in production. The point of this branch is to learn Kubernetes, so it is the opposite of the experiment.

So: nginx is the smallest way to keep the backend untouched. If you later add CORS to the Worker, you can swap nginx for any static server.

6. Try it

make k8s-up       # create the cluster, build + load the image, apply k8s/
make k8s-open     # http://localhost:8080 (Ctrl-C to stop)
kubectl --context kind-thumbnail get pods,svc
kubectl --context kind-thumbnail logs deploy/thumbnail-frontend    # nginx access log: see /api requests
make k8s-down

Needs Docker running, plus kind and kubectl (brew install kind).
