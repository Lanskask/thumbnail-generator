1. What Helm is, and your first release

Plain Kubernetes YAML is fixed text. To run the same app twice (say dev with 1 copy and prod with 3) you would copy the files and edit them. Helm is a package manager for Kubernetes: it turns YAML into templates with blanks, and fills the blanks from values.

TermMeaning
ChartA folder: templates + default values + metadata. The "package".
ReleaseOne installation of a chart in a cluster, with a name. Installing the same chart twice gives two releases.
ValuesThe settings you give the templates (values.yaml, -f file, --set key=val).
RevisionEach install or upgrade of a release is a numbered revision. That is what makes rollback possible.

Helm 3 has no server part: the helm program talks to the cluster with your kubeconfig and keeps release records as Secrets in the namespace.

Exercise 1: scaffold and install a chart

mkdir -p ~/helm-course && cd ~/helm-course
helm create hello
ls hello hello/templates
helm install hello1 ./hello
helm list
kubectl get pods,svc
  1. Which files did helm create make? What is the name of the Pod?
  2. Reach the app: kubectl port-forward svc/hello1-hello 8081:80, then open http://localhost:8081.
  3. Remove it: helm uninstall hello1. What happened to the Pods?
Show solution

The Pod is named like hello1-hello-<hash>: the release name is part of every object's name. That is how two releases of one chart avoid colliding. You see the nginx welcome page. After uninstall, every object the release created is deleted, because Helm remembers what it created.

2. Templates and values

Look at hello/templates/deployment.yaml. Pieces between {{ }} are Go template actions. The ones you need first:

ExpressionGives
{{ .Values.replicaCount }}A value from values.yaml (or an override)
{{ .Release.Name }}The name you gave at helm install
{{ .Chart.Name }}, {{ .Chart.AppVersion }}Fields of Chart.yaml
{{ .Values.image.tag | default .Chart.AppVersion }}A pipe: use the tag, or the fallback if empty
{{ .Values.x | quote }}Wraps in quotes (important for strings that look like numbers)

Override order, lowest to highest: chart's values.yaml, then -f file.yaml, then --set.

Rendering without touching the cluster is the most useful debugging tool you have: helm template.

Exercise 2: see what values do

helm template demo ./hello | head -60
helm template demo ./hello --set replicaCount=3 | grep replicas
helm template demo ./hello --set image.tag=1.27 | grep image:
printf 'replicaCount: 2\n' > my-values.yaml
helm template demo ./hello -f my-values.yaml --set replicaCount=5 | grep replicas
  1. What is the last command's replica count, and why?
  2. Run helm install demo ./hello --dry-run --debug. What does it print that template does not?
Show solution

1. 5: --set beats -f, which beats the chart default. 2. It also prints the computed values and the release metadata, and it asks the cluster to validate the objects, so it catches errors that template cannot.

3. Build the thumbnail-frontend chart

Now the real thing. Turn k8s/frontend.yaml into a chart with three knobs: replicas, image, and the backend host.

Exercise 3

From the repo root, create charts/thumbnail-frontend/ with:

  • Chart.yaml: apiVersion: v2, a name, version: 0.1.0, appVersion: "dev"
  • values.yaml: replicaCount, image.repository, image.tag, backendHost
  • templates/deployment.yaml and templates/service.yaml: the two objects from k8s/frontend.yaml, with names starting from {{ .Release.Name }}

Install as release fe, forward its Service to port 8082, and upload an image through the page.

Check: helm list shows fe as deployed, and the page works at http://localhost:8082.

Show solution 
# charts/thumbnail-frontend/Chart.yaml
apiVersion: v2
name: thumbnail-frontend
description: nginx serving the upload page and proxying /api to the Cloudflare Worker
version: 0.1.0
appVersion: "dev"

# charts/thumbnail-frontend/values.yaml
replicaCount: 1
image:
  repository: thumbnail-frontend
  tag: dev
backendHost: thumbnail-generator.physics-study-dashboards.workers.dev

# charts/thumbnail-frontend/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-frontend
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}-frontend
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-frontend
    spec:
      containers:
        - name: nginx
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80
          env:
            - name: BACKEND_HOST
              value: {{ .Values.backendHost | quote }}
          readinessProbe:
            httpGet:
              path: /
              port: 80

# charts/thumbnail-frontend/templates/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-frontend
spec:
  selector:
    app: {{ .Release.Name }}-frontend
  ports:
    - port: 80
      targetPort: 80
helm install fe charts/thumbnail-frontend
kubectl port-forward svc/fe-frontend 8082:80

The release is called fe, so the objects are fe-frontend, not thumbnail-frontend. That avoids a clash with the plain-YAML copy from make k8s-up; Helm refuses to take over objects it did not create.

4. Upgrade, history, rollback

helm upgrade re-renders the chart with new values and applies the difference, creating a new revision. Helm keeps the old ones.

Exercise 4

helm upgrade fe charts/thumbnail-frontend --set replicaCount=3
kubectl get pods -l app=fe-frontend
helm upgrade fe charts/thumbnail-frontend --set backendHost=does-not-exist.invalid
helm history fe
helm get values fe
  1. Open the page and upload an image. What breaks, and where do you see it? (hint: kubectl logs deploy/fe-frontend)
  2. Undo the bad change: helm rollback fe 2. Then run helm history fe: how many revisions are there now?
  3. Why did the second upgrade reset replicaCount to 1?
Show solution

1. nginx cannot resolve the host, so /api returns 502 Bad Gateway; the log shows the "could not be resolved" error. (Because nginx resolves the name at start, the new Pods may even fail to become ready; kubectl get pods shows that.)

2. Four: a rollback is itself a new revision (4) that copies revision 2.

3. --set only applies to that one command. Helm does not remember it unless you pass --reuse-values. The reliable habit is a values file (-f prod.yaml) kept in git, so every upgrade states the full desired setup.

5. Conditionals, helpers, and an optional Ingress

Templates can branch and loop. Two things to learn:

{{- if .Values.ingress.enabled }}
...an Ingress object...
{{- end }}

The - in {{- trims the blank line before it, which keeps the YAML valid. Repeated text goes in a named template in templates/_helpers.tpl (files starting with _ produce no object):

{{- define "thumbnail-frontend.fullname" -}}
{{ .Release.Name }}-frontend
{{- end }}

Use it with {{ include "thumbnail-frontend.fullname" . }}. The trailing . passes the current context.

Exercise 5

  1. Add _helpers.tpl with the helper above, and replace the four copies of {{ .Release.Name }}-frontend with include.
  2. Add templates/ingress.yaml that renders only when ingress.enabled is true (default false in values.yaml), with host from ingress.host.
  3. Check with helm template fe charts/thumbnail-frontend that there is no Ingress, and with --set ingress.enabled=true --set ingress.host=thumb.local that there is exactly one.
Show solution 
# values.yaml (add)
ingress:
  enabled: false
  host: thumb.local

# templates/ingress.yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "thumbnail-frontend.fullname" . }}
spec:
  rules:
    - host: {{ .Values.ingress.host | quote }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: {{ include "thumbnail-frontend.fullname" . }}
                port:
                  number: 80
{{- end }}

An Ingress only does something if an Ingress controller (for example ingress-nginx) runs in the cluster, which a fresh kind cluster does not have. So the object renders and applies, but nothing serves it. That is why the switch defaults to off.

6. Lint, package, and where to go next

Exercise 6

helm package charts/thumbnail-frontend          # -> thumbnail-frontend-0.1.0.tgz
helm install fe2 ./thumbnail-frontend-0.1.0.tgz --set replicaCount=2

helm uninstall fe fe2

  2. Install the chart twice (fe and fe2). Why do they not collide?
  3. Add a Makefile target helm-up that runs helm upgrade --install fe charts/thumbnail-frontend. Why is upgrade --install preferable to plain install in scripts?
Show solution

2. Every object name starts with the release name. 3. It installs if the release is missing and upgrades if present, so the same command works the first and the hundredth time.

Cheat sheet

helm create NAMEscaffold a chart
helm template REL CHARTrender locally, no cluster
helm lint CHARTcheck for mistakes
helm upgrade --install REL CHART -f values.yamlinstall or update
helm list, helm history REL, helm get values REL, helm get manifest RELinspect
helm rollback REL REVISIONgo back
helm uninstall RELdelete everything the release made
